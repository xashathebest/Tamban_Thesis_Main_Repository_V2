# 04 — Settings and checkpoint integrity

`src/api/app.py:_update_settings_locked` validates supported keys, aliases, types, ranges, display fields and model compatibility before committing. It rolls software settings back if application or session rotation fails. `_model_change_lock` serializes settings requests and guards active inspection changes; cosmetic display settings remain available. Camera controls separately preflight and attempt restoration on driver failures, while reporting actual readback if restoration fails.

The model registry resolves checkpoint paths; registered SHA-256 values are compared at load/switch, not for each frame. Explicit IDs must match resolved checkpoint paths; unknown custom checkpoints are labeled unverified and cannot run under strict integrity mode. Session snapshots include loaded IDs, hashes, configuration and configuration hash. Absent checkpoints report unavailable rather than being assumed corrupt. Hashing and opening are separate operations, so replacement between them remains a limitation.

`tests/test_settings_atomic_qa.py` now also runs two concurrent settings requests and verifies that the second cannot complete inside the first update and that the resulting detector/state values agree. Existing tests cover invalid mixed payloads, rollback, rotation, active-session locks, hash mismatch and explicit path identity.
